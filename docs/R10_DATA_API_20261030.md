## Control reutilizable

El workflow se activa en TODOS los pull requests dirigidos a `main`, sin filtro por rutas. Una propuesta que solo añada una migración ya no puede omitir esta comprobación. No se activa por push a producción, no despliega y no usa `pull_request_target`. No se han cambiado las reglas de protección de rama: que un control se ejecute no significa que GitHub lo haya configurado como obligatorio para fusionar.

Se conserva el ancla histórica, no una lista cerrada de los cinco archivos de la auditoría. El planificador comprueba los hashes de las once fuentes históricas, la base SQL y la configuración LOCAL. Detecta todos los SQL posteriores del directorio, ordena por versión, rechaza versiones duplicadas o atrasadas, rutas peligrosas, enlaces simbólicos, archivos sin inventariar y hashes distintos. Las 39 fuentes históricas ausentes no se inventan: se reconstruye la base sanitizada y sus ocho ampliaciones conocidas.

Cada SQL nuevo debe estar inventariado en `production-ledger-current.json` o `pending-migrations.json`, y debe declarar pruebas ejecutables y su intención de acceso en `supabase/tests/data-api-contracts.json`. La suma de ambos inventarios debe cubrir exactamente todos los archivos. El contrato no aplica permisos: solamente describe lo esperado y lo verifica.

Formato ilustrativo de una entrada (el nombre REAL se genera con `supabase migration new`):

```json
{
  "file": "AAAAMMDDhhmmss_nombre.sql",
  "tests": ["supabase/tests/database/nombre.test.sql"],
  "tables": {
    "public.nueva_tabla": {
      "anon": [],
      "authenticated": ["SELECT"],
      "service_role": []
    }
  }
}
```

Para una tabla interna se declaran los tres roles con listas vacías. Una migración sin nuevas tablas usa `"tables": {}` y conserva sus pruebas obligatorias. Toda tabla nueva debe quedar declarada. Una tabla existente cuyo acceso cambie deliberadamente también debe declararse. Se rechazan permisos anónimos de negocio y permisos administrativos en contratos nuevos. Los cambios de vistas, secuencias, funciones y efectos funcionales deben comprobarse en las pruebas específicas; no se pretende inferir la intención del SQL ni sustituir su revisión.
