Esta propuesta no modifica frontend, base estructural, migraciones históricas, Edge Functions, automatización de copias ni workflows existentes. No es una autorización de fusión, despliegue o cambio de permisos remotos.

**El proyecto cuyo nombre contiene STAGING es producción**; no se utiliza aquí. Tampoco se utiliza ni reactiva el proyecto temporal de restauración. No se crean proyectos o ramas facturables de Supabase.

## Evidencia que produce la prueba

1. Runner desechable de GitHub con CLI 2.115.0 y PostgreSQL 17, como la barrera existente; checkout sin persistir credenciales y token limitado a lectura. Sin secretos remotos.
2. Verificación de SHA-256 de la base estructural y rechazo de modificaciones fuera de los cinco archivos de esta propuesta.
3. Esquema local inicialmente vacío. Revocación de los defaults de tablas y secuencias descritos en el anuncio, ANTES de reconstruir. Una tabla y secuencia de control demuestran que los defaults ya no conceden acceso.
4. Preparación del destino idéntica a la que ya usa `scripts/restore_from_local.sh` del repositorio de copias (`95838ed7411ecbc14d2e4e8d6e480b34adae8761`): `ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES FROM anon, authenticated`. Se aplica solo al destino local vacío. Después, restauración de la base sanitizada y de las ocho migraciones posteriores, conservadas literalmente. Las migraciones históricas son parciales: no se simula incorrectamente que `db reset` basta para reconstruir todo el CRM.
5. Las nueve suites SQL existentes se ejecutan bajo el nuevo escenario. Una décima verifica permisos explícitos, RLS, backend e invariancia de permisos existentes al cambiar defaults. La transición se simula dentro de una transacción revertida.
6. Pruebas HTTP contra `127.0.0.1:54321`: denegación sin GRANT, lectura limitada por RLS tras GRANT, denegación anónima y de escritura directa, separación de dos comerciales, acceso de propietario y administración y edición de nombre/teléfono/email mediante la RPC vigente.
7. Los únicos trabajos Cron activos admitidos son controles inertes `select 1`, `select 2` o `select 3`. No se invocan Edge Functions ni correos. El entorno se detiene al terminar, también ante un fallo.

El archivo temporal que contiene claves del stack LOCAL no se imprime ni se sube como artefacto. El artefacto conserva solamente resultados de pruebas y datos sintéticos. Se rechazan destinos HTTP distintos de localhost, proxies y redirecciones. `psql` recibe un entorno limpio y destino local fijo.

## Interpretación y límites

Una ejecución verde demuestra compatibilidad de la reconstrucción estructural probada y de estos contratos de acceso; NO demuestra restauración completa de una copia de datos real, recuperación de Vault/pgSodium, SMTP ni equivalencia integral de producción. No se ejecuta ninguna migración nueva en producción. El workflow previo de barrera R10 se conserva y también se ejecuta con el PR.

La auditoría previa observó 21 tablas con RLS, 14 tablas con SELECT autenticado y 50 migraciones aplicadas. Los permisos adicionales de `operator_presence` y defaults administrativos heredados se documentan como cuestión separada: estas pruebas no los revocan ni declaran resuelta una auditoría general de seguridad.

Si una prueba falla, no se deben añadir grants generales ni desactivar RLS para hacerla pasar. Primero se identifica el objeto y la dependencia exacta. Cualquier corrección funcional requeriría otra revisión y autorización antes de producción.

## Incidencias del arnés detectadas y corregidas

- Primera ejecución: las nueve suites existentes pasaron; una comparación nueva de nombres del catálogo falló por collation ambigua. Se corrigió exclusivamente el test usando comparaciones con collation C.
- Segunda ejecución: 205 de 206 aserciones pasaron. El control estricto de permisos anónimos detectó privilegios administrativos heredados al importar la base sobre defaults locales parcialmente revocados. El arnés había omitido la preparación que ya existe en el script real de restauración. Se incorporó ese paso previo, manteniendo el control estricto, sin alterar la base SQL, las migraciones históricas ni la configuración remota. La siguiente ejecución debe confirmar esta corrección; una hipótesis no se considera validación.

La diferencia es relevante: el cambio oficial retira permisos CRUD automáticos; no es una limpieza general de todos los privilegios de un destino. Para reconstruir se debe conservar el procedimiento completo de preparación del destino y verificar el resultado, no importar solamente el SQL.
